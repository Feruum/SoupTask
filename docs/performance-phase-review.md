## What the hot path actually does

- `src/charts/MetricPlot.tsx:336` maps pointer position to a source step and deduplicates the scale/step key at `:357`. Both `pointerrawupdate` and ordinary `pointermove` enter this adapter (`:405`, `:409`), so the later coalesced pointer event can follow a completed raw-input update without a second source request.
- `src/worker/use-workspace.ts:220` starts the intent clock, tries the accepted-view source cache, and synchronously accepts a cache hit through the controller. Acceptance records timing and publishes one cursor snapshot (`:124`–`:133`). No raw-array scan is added to the main thread by this review.
- `src/worker/cursor-store.ts:23` calls the before-publish adapter before its subscribers. `ComparisonCursorReadout.tsx:75` uses this to arm a RAF early. Its subscriber updates existing leaf nodes, then records commit (`:51`–`:73`). The early RAF and commit share one epoch/view/hover key.
- `src/charts/use-hover-paint.ts:5` keeps one pending frame. A different key cancels the previous pair; the same pending key returns it (`:10`–`:12`). The first callback requires committed DOM (`:14`–`:16`), and the second requires current identity plus non-hidden, laid-out readouts (`:17`–`:23`). Completion cancels/clears its own handles. Changing to a single RAF, accepted response, or DOM commit would change the requested endpoint.

### Supersession/cancellation audit

There are zero pre-frame `CancelAnimationFrame` events, zero `soup:charts-render` or `soup:source-readout-render` marks, and the intended two RAF callbacks fire. ## Timing wrapper assessment and limits

`src/app/performance.ts:4` performs a fixed-name Map lookup/set and only clears the matching mark/measure bucket at its 128-entry boundary. It does not schedule RAFs, query DOM, or retain a sequence of callback chains. The saved trace has `FunctionCall` locations and rendering events but no CPU-profile sample stream that isolates the inner `reserve()` / `clearMarks()` / `clearMeasures()` functions. The p95 Compare window has a native `UserTiming::Measure` record lasting **0.027 ms**; all 66 such records in its Compare trace have p95 0.194 ms, max 0.225 ms. Those records measure that native operation, not the complete JavaScript wrapper or every mark call.

Accordingly, the evidence does not prove that the 128-entry wrapper causes, or is free of, every small overhead contribution. It does rule out presenting a measured large wrapper stall: no such isolated measurement or stack is present. In the concrete high windows, source acceptance and DOM commit complete long before the delayed RAF opportunities. Both prior-release and candidate runs vary, and removing trace recording improves the endpoint, but that alone cannot identify which recording category, scheduler effect, application invalidation, or host condition accounts for each missing frame.

This review therefore leaves the at-most-50-ms full-recording performance acceptance **unmet**, while preserving the required endpoint and the passing correctness/lifecycle work. It does not recommend selecting the best run, weakening the endpoint, changing the harness, or modifying frozen source without a demonstrated expensive operation to address.

### Layout and CSS hypothesis

The parent identified a concrete CSS mismatch worth testing: global `.chart-hover-value` supplies `font-variant-numeric:tabular-nums` and a border radius, while the earlier `.rail > .content` override reset margin/padding/border/background but did not reset those two properties. Toggling the class could therefore change inherited font formatting and the paint-contained clipping shape. Setting permanent tabular numerals and radius zero on `.content` makes those computed properties invariant across view-clear/hover entry. That source/CSS hypothesis is valid; its contribution to layout/paint duration still needs measurement. It is not evidence that this small change alone guarantees the latency target.

At desktop viewport dimensions of at least 1100×700 CSS pixels, the shared rail is fixed above the bottom edge. The shell's main area becomes a bounded scroll region with member-count-dependent reserved space above that rail. Its dimensions do not depend on whether the cursor is active, so entry does not itself create/remove the dock. Below the media threshold the table retains its ordinary in-flow, keyboard-scrollable behavior. The marker class `.source-dock-layout` is not the mechanism that performs the scrolling; the actual rules are the scoped `body:has(.sharedRail)` CSS. Tests that infer document position using only `window.scrollY` must account for the actual scroll ancestors after this layout change.

### Accurate limits of the validator

- The clipping recursion resets to the viewport at any fixed-position ancestor. That matches the current dock, whose ancestors above the fixed rail do not establish a transformed/filtered/paint-contained fixed containing block. It is not a general implementation of fixed-position containing-block rules for arbitrary future ancestors.
- The optimized occlusion check samples the **center of each actual cell text range**. Full text-bound containment is still checked, but a center hit does not prove every physical glyph pixel is unobscured. An overlay covering only another part of the cell, or an opaque overlay with `pointer-events:none`, can escape this occlusion sample. Current negative controls cover a fully covering, hit-testable overlay; they do not certify all possible occlusion geometry.
- The shared-table contract examines the first visible row in each body. It does not certify the second displayed duplicate-source row, every source action, or all horizontally/vertically scrollable content at once. On narrow in-flow layouts or long duplicate groups, a truthful rejected acknowledgment is possible until the required cells are visible. Rejection is not itself a source-data failure.
- Visibility is checked at the second RAF callback. It establishes geometry, sampled ownership and a rendering opportunity, not physical monitor presentation, screen-reader usability or universal accessibility. Changes after the callback are outside that sampled instant.

The new positive tests explicitly wait for a frame matching the current accepted hover, then independently inspect actual source-cell text bounds and hit-test ownership. The negative cases move the dock offscreen, clip the content and cover it with an overlay, and require rejection rather than a successful current frame. Those are useful behavior controls. The lead agent reports an 18/18 targeted green run; I inspected test logic but did not independently execute it. The provided cases focus on 1440×900 shared-table layouts (four cells for Run, sixteen for four-run Compare); they do not replace mobile/duplicate-group/full-suite acceptance.

The lead agent also reports concrete self-cost in the first new full trace: the five-points-per-cell validator performed 80 hit tests and consumed approximately 18–19 ms inside a 54 ms RAF. That is a measured new expensive phase, unlike the earlier unproven timing-wrapper hypothesis. I inspected the subsequent optimization to immutable computed-property snapshots, memoized ancestor visibility and one hit test per cell. It reduces repeated work while preserving full text clipping checks, with the reduced occlusion scope stated above. `verificationMs` and the frame clock are recorded after verification, so its cost remains included in the required endpoint. I did not independently parse that new trace or assert a measured speedup from the revised validator; fresh full-trace results are required.
