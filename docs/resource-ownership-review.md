## Review conclusions

**Design and concurrency.** Ownership is local and explicit. Raw/index state stays in the Worker, accepted render data stays with the UI, and cache entries are copied source rows for one view. The request bound is enforced before `postMessage`, so rapid pointer/view activity does not create an unbounded Worker message backlog. Identity checks cover activation, selection, member revision and member activation epoch (`src/worker/protocol.ts:33`), including A to B to A. Request IDs reject duplicate replies; view/hover/inspection sequences reject superseded operations. Disposal drops both controller slots and severs external event entry points.

The hook does not eagerly null every cache/cursor/view ref in its unmount cleanup (`src/worker/use-workspace.ts:157`). That is **not an accumulating leak demonstrated by this source**: the owning hook can be collected, and any React-retained hook keeps a bounded current snapshot. Activation and view replacement clear those refs. `prepareHover` has at most one queued microtask; it cannot be canceled, but the origin/current-view check rejects replaced views and the disposed controller rejects requests after teardown. Clearing more refs would be an optional eager-release optimization, not a required fix supported by the current evidence.

**Native binder compatibility.** The installed uPlot implementation calls `cursor.bind[ev](self, target, handler, onlyTarg)` and dynamically reads `cursor.bind` when drag begins. The wrapper is therefore installed in time. `Reflect.apply(..., args)` preserves the fourth argument; destructuring only the three declared TypeScript arguments would have changed outside-target drag behavior. Cloning `active.cursor.bind` avoids mutating a potentially shared library configuration object. The map retains at most the active chart's target/listener entries and is cleared on teardown. Normal mouseup already removes its document listener; removing it again during cleanup is harmless.

**Complexity and scope.** The fixes address the diagnosed lifetimes directly: bounded timing entry retention, bounded formatter reuse, release of bitmap dimensions, and cleanup of a specific external listener. They introduce no changes to source numeric values, sampling, index selection, or row alignment. Chart/readout files have substantial existing responsibilities, but this change does not justify an unrelated refactor. The type-only imports from cursor readouts back to the `Workspace` feature type are coupling worth considering during a future interface extraction (`src/charts/SourceCursorReadout.tsx:7`, `src/charts/ComparisonCursorReadout.tsx:6`); they are erased imports and do not establish a runtime lifecycle defect or merge blocker.

**Useful tests.** New unit tests exercise real Performance entries, latest mark/measure endpoints and detail values (including negative zero), preservation of unrelated entries, actual timestamp output, constructor reuse, and FIFO eviction. The new E2E cases inspect application marks after repeated pointer input, retain real old Canvas nodes to prove dimensions are zeroed without relying on GC, and enumerate native document event listeners during an interrupted real mouse drag. The latter observes that the listener exists before leaving and is absent before the eventual mouseup, so a normal release cannot hide missing teardown. These are behavior assertions rather than implementation-only snapshots. Existing controller/cache/race tests inspect bounded queues, stale successes/errors, revision/epoch mismatch, post-disposal replies, and transfer/source ownership. This reviewer inspected test logic but did not independently verify execution or the reported red/green runs.

## Evidence and limits

The supplied `reports/memory-investigation-2026-11-10/interrupted-drag-before/retainer-analysis.json` explicitly describes an independent implementation of MemLab's baseline/target/final set-difference method, not execution of the MemLab CLI. Its one-transition result lists 202,815 candidate objects, 687 detached candidate nodes and 10 chart/Canvas candidate nodes. Those counts are candidate sets, not a list of proven leaks.

The concrete actionable path is `HTMLDocument -> EventTargetData -> RegisteredEventListener -> EventListener -> V8EventListener -> uPlot mouseup callback -> closure context -> uplot root/Canvas or retained event path`. This matches the installed dependency: uPlot `destroy()` clears its listener bookkeeping Map but does not call the removal routine for a still-registered document mouseup listener. The adapter's explicit removal addresses that root.

The same artifact also contains a separate native Window listener/closure path through V8 allocation-site feedback, accessor getter context, `cursor.dataIdx`, and plot context. The presence of a strong path alone does not show that this is an accumulating application registration. Engine feedback, bounded React alternates, font/Intl caches and loaded modules require separate disposition; this review does not label all remaining detached nodes as leaks.

Post-fix B/T/F and native-memory artifacts are now available and reviewed in the final-validation section below. This reviewer did not modify report artifacts or start competing browser/profiler sessions. Static source review alone cannot infer native backing-store bytes or OS reclamation from Canvas dimensions and JS heap candidates.

### Native attribution versus natural process memory

The forced-snapshot diagnostic comparison is [pre-artwork native attribution at `3ee28c5`](../reports/memory-investigation-2026-11-10/interrupted-drag-after/native-attribution.json) against [final native attribution at `cd01873`](../reports/memory-investigation-2026-11-10/final-roundtrip/native-attribution.json). These are category/provider values associated with diagnostic dump spans. Heap snapshots force GC and load profiler metadata, so these numbers cannot be presented as natural-GC process-memory results. Categories must not be added to OS footprint or described as total GPU/tab memory.

The separate no-forced-GC Windows-counter experiments show the practical limit. [Final natural run](../reports/memory-investigation-2026-11-10/final-memory-fixed/results.json) and [repeat](../reports/memory-investigation-2026-11-10/final-memory-fixed-repeat/results.json) start the settled 1M view at 147.24/145.69 MiB private committed memory. That private committed result is effectively unchanged at this measurement resolution and sample count. Working set after 20 switches is 376.14/375.88 MiB versus 444.87 MiB before. The reported scope deduplicates renderer/live-Worker PIDs; process counters are sequential and are not universal total tab/GPU memory.
