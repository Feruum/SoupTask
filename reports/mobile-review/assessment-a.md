## Design specificity

Strong and product-specific. The circular experiment instrument, model → method → run tree, source findings rail, restrained orange/teal/ochre/purple system, and modest pixel ornament make this clearly Soup's Kazakh training workspace. The desktop dashboard has a coherent, unusually memorable composition. Preserve that composition. The mobile adaptation preserves the visual identity but currently preserves desktop reading order too literally: the user gets the visual instrument before the compact operational information needed to act.

## Priority defects

1. **P1 — Mobile run rows hide the useful comparison and inspection information.** At 390px the runs table shows the checkbox and run identity; status, latest loss, step, quality and Preview are offscreen horizontally. The full render confirms the preview is after all 20 rows. Selecting Preview consequently updates a panel far from the control, with no immediate visible result at the current row. This is two-dimensional browsing for the main task. Use a mobile row/card presentation with run identity, status, latest loss, quality, selection and open/preview actions together; keep the desktop table. Sources: `src/features/runs/RunsPage.tsx:52`, `:57`; `src/styles/theme.css:115`, `:117`, `:299`. Evidence: `dark-390-runs-viewport.png`, `dark-390-runs-full.png`.

2. **P1 — Dashboard selected-run result is too far below its selection instrument.** The first 390px screen is entirely heading, metric tabs and map. The native run selector comes after the map; the selected-run facts and Open/Compare/Inspect actions follow both that block and the experiment groups. A user changes a run and must scroll through a separate relationship view to see its result. Keep the circular map and desktop layout, but on mobile place a compact selected-run summary/action block immediately beside/after the selectors, with groups and explanatory detail disclosed later. Sources: `src/features/dashboard/DashboardPage.tsx:71`–`:90`; `src/features/dashboard/dashboard.css:113` mobile stacking rules; `src/features/dashboard/ExperimentMap.tsx` selector/details block. Evidence: `dark-390-dashboard-viewport.png`, `dark-390-dashboard-full.png`, `light-320-dashboard-viewport.png`.

3. **P1 — Data quality hides the investigation entry point behind the full matrix.** The 390px view exposes run, loss and learning rate only; remaining quality columns require horizontal browsing. The full render places the run/metric/type controls and source ledger after all 20 matrix rows. Even after a finding is selected, source inspection is a long vertical journey and still a wide table. Provide a compact mobile quality list, show issue-bearing runs clearly, and position the active investigation controls/result before or immediately after the selected run; keep the matrix available as secondary detail. Sources: `src/features/quality/QualityPage.tsx:41` and following matrix/ledger JSX; `src/styles/theme.css:115`, `:117`, `:295`. Evidence: `dark-390-quality-viewport.png`, `dark-390-quality-full.png`.

4. **P2 — Compare requires rediscovering an already-made selection.** The direct URL contains runs 005 and 006, but the first screen starts an all-runs chooser at 001; 005 is clipped at the lower edge and 006 is below it. The heading says “2 runs selected” without naming them. Four static comparison facts sit before metrics/range/chart controls. Put selected run chips and their remove controls first, collapse the all-run chooser into “Edit selection,” and disclose alignment details. Sources: `src/features/compare/ComparePage.tsx:56`; `src/styles/theme.css:161`–`:172`, `:301`. Evidence: `dark-390-compare-viewport.png`.

5. **P2 — Small-phone layout substantially delays measurements, and chart guidance is desktop-only.** At 320px run summary cards switch to one column, showing only two of four cards before the bottom bar; charts and range controls are further down. Mobile tabs horizontally clip “Run information” without an obvious overflow cue. Charts repeat “Wheel / Ctrl+wheel / Shift+wheel / Drag” even at touch widths. Keep concise summary pairs where values fit or disclose secondary facts; make tab overflow discoverable and give touch-appropriate chart guidance while preserving explicit range buttons. Sources: `src/styles/theme.css:302`, `:268` section tabs; `src/features/shared/Workspace.tsx:165`; `src/features/runs/RunPage.tsx:43`. Evidence: `light-320-run-viewport.png`, `dark-390-run-viewport.png`.

## Cognitive load

**High: five checklist failures in the combined mobile journey.** Intrinsic complexity is justified: comparing raw training measurements and auditing their provenance is a demanding task. The avoidable load comes from layout travel and hidden relationships.

| Checklist | Result | Reason |
|---|---|---|
| Single focus | Fail | Runs opens with overview cards and five filter/sort controls before any result. Dashboard instrument and relationship tree precede its operational summary. |
| Chunking | Pass | Four summary cards and small groups are generally well chunked. |
| Grouping | Pass | Boundaries, spacing and section headings express related content clearly. |
| Visual hierarchy | Fail on mobile | The strongest first-screen area is often context/visualization rather than the immediate result or investigation action. Desktop hierarchy is strong. |
| One thing at a time | Pass | Controls are labeled and the user can operate a single filter or selector at a time. |
| Minimal choices | Fail | Runs exposes search, status, quality, sort and direction together (five); compare exposes a 20-run selection collection; the radial map has 60 run/metric sectors. Search/native selectors mitigate but do not fully resolve the initial choice burden. |
| Working memory | Fail | Horizontal table scrolling separates identities from later columns; compare names need rediscovery; previews are separated from the initiating row. |
| Progressive disclosure | Fail | Entire matrices and chooser/context blocks precede primary mobile results; accessible map table is a good exception because it is already disclosed. |

Decision points above four options: five runs filter/sort controls; twenty possible comparison runs; twenty experiment choices (native select, an acceptable mitigation); sixty radial run/metric targets. The map is best treated as an overview plus native selection path on a phone, rather than sixty equally usable touch targets. No exact target measurements were made in this assessment.

## Strengths and emotional journey

- The four labeled bottom destinations have clear active feedback and remain visible, providing orientation throughout long pages. Safe-area padding is present in source.
- Desktop has a clear instrument → selected run → source findings relationship. Brand-specific geometry and the modest ornament add character without undermining scientific credibility.
- “Original values,” immutable source references, revision checks and explicit invalid/gap counts support trust. Native selects and the accessible radial table give useful alternatives to a complex visualization.

Initial impression is confident and capable. The emotional valley occurs when the mobile user tries to act: the promise of immediate preview, comparison or source inspection becomes horizontal or long vertical travel. Source provenance and actionable recovery copy provide reassurance at the end, but that reassurance arrives late. The most valuable correction is proximity between intent and result.

## Persona red flags

- **Casey, distracted mobile user:** small run-row checkboxes have no expanded row label hit area; preview and quality investigation need substantial page travel; offscreen actions demand sideways browsing. This is source/visual evidence, not a measured touch-target audit.
- **Alex, power user:** good search and exact-source tools are present, but the mobile table/preview separation slows repetitive scanning; compare requires rediscovering selected run identities.
- **Sam, accessibility-dependent user:** labeled navigation, skip link, focus styles, native selectors and map keyboard controls are positive. Reflow still relies on nested table overflow, and map label text becomes very small visually. Screen-reader behavior remains untested.

Minor observations: mobile header retains useful workspace identity but hides Soup wordmark and “Demo data”; demo status remains explicit on run/compare/quality headings. Dashboard duplicates metric selection in top tabs and a native select, which helps access but also increases vertical context. The 320px summary breakpoint is a larger usability regression than any missing decoration.
